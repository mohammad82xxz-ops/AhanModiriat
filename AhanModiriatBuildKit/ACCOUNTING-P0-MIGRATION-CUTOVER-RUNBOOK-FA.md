# دستورالعمل ایمن مهاجرت، برش و بازگشت P0 حسابداری

> وضعیت: Runbook طراحی؛ مجوز اجرای مهاجرت روی دیتابیس واقعی نیست.  
> شاخه: `rebuild/phase1-money-rial-foundation`  
> مرجع: برنامه P0، نقشه اتصال کد و سناریوهای طلایی.  
> اصل: هیچ migration روی دیتابیس واقعی بدون backup قابل‌بازیابی، اجرای آزمایشی روی clone و تأیید مالک انجام نشود.

## ۱. هدف و محدوده

این سند پیش‌بررسی، backup، مهاجرت shadow، تطبیق، cutover، پایش و rollback را تعریف می‌کند. این سند DEC-01 تا DEC-10 را تصویب نمی‌کند و جایگزین سناریوهای طلایی نیست.

## ۲. پیش‌شرط‌های شروع

- [ ] مالک کسب‌وکار تصمیم‌های سیاستی لازم را مکتوب و نسخه‌دار تأیید کرده باشد.
- [ ] کد و schema مقصد در commit مشخص و بازبینی‌شده باشند؛ working tree پاک باشد.
- [ ] CI و تست‌های واحد، integration، golden، migration و restore روی همان SHA سبز باشند.
- [ ] نسخهٔ Python، SQLite، dependencyها و تنظیمات runtime ثبت شده باشند.
- [ ] مسیر دیتابیس و فایل‌های جانبی SQLite مانند WAL و SHM شناسایی شده باشند.
- [ ] زمان توقف نوشتن داده و مسئول اجرای عملیات مشخص شده باشد.
- [ ] backup مستقل با checksum ساخته شده باشد.
- [ ] restore همان backup روی مسیر آزمایشی با موفقیت انجام شده باشد.
- [ ] snapshot تعداد رکوردها، موجودی، ارزش، مانده اشخاص و حساب‌های نقد تهیه شده باشد.

اگر حتی یک پیش‌شرط برقرار نیست، عملیات متوقف شود.

## ۳. پیش‌بررسی (Preflight)

1. نسخهٔ برنامه، commit، schema version و migration version را ثبت کن.
2. مسیر دیتابیس فعال را از تنظیمات runtime بخوان؛ مسیر را حدس نزن.
3. برنامه را در حالت maintenance قرار بده و همهٔ نویسنده‌ها/workerها را متوقف کن.
4. اتصال‌های باز را ببند و نبود process نویسنده را تأیید کن.
5. PRAGMA integrity_check و PRAGMA foreign_key_check را اجرا و خروجی را ذخیره کن.
6. تعداد ردیف تمام جدول‌های مالی و مرجع را snapshot کن.
7. جمع‌های کنترل مستقل را استخراج کن: مقدار/وزن/ارزش هر کالا، ماندهٔ هر شخص، ماندهٔ هر حساب نقد/بانک، تعداد اسناد و جمع مبالغ.
8. داده‌های مبهم، مقدارهای خارج از محدوده، نام‌های تکراری، واحدهای نامعلوم و ارجاع‌های شکسته را در exception report ثبت کن؛ اصلاح حدسی ممنوع است.

**شرط توقف:** فساد SQLite، FK شکسته، مبلغ/مقدار خارج از محدوده یا اختلاف حل‌نشده در جمع‌های کنترلی.

## ۴. Backup و اثبات قابلیت بازیابی

- از روش سازگار با SQLite برای snapshot یکپارچه استفاده شود؛ کپی خام فایل هنگام فعال بودن WAL به‌تنهایی backup معتبر محسوب نشود.
- backup در محل مستقل با نام شامل تاریخ، محیط و SHA کد ذخیره شود.
- SHA-256، اندازه، زمان ساخت و نسخهٔ برنامه ثبت شود.
- restore به مسیر جدید و خالی انجام شود؛ هرگز روی فایل اصلی restore نکن.
- روی clone بازیابی‌شده، integrity_check، foreign_key_check، شمارش ردیف‌ها و جمع‌های کنترلی تکرار شود.
- فایل اصلی تا پایان پایش دست‌نخورده و قابل بازگشت بماند.

**معیار قبولی:** backup فقط وقتی معتبر است که restore واقعی و تطبیق جمع‌های کنترلی موفق شده باشد.

## ۵. مهاجرت Shadow

1. clone تهیه‌شده از backup را به‌عنوان source ثابت کن.
2. migration را روی کپی تازه‌ای از source اجرا کن؛ اجرای آزمایشی روی فایل اصلی ممنوع.
3. نسخهٔ migration و checkpoint هر مرحله ثبت شود.
4. هر رکورد مقصد باید شناسهٔ منبع خود را نگه دارد.
5. دادهٔ مبهم وارد exception report شود؛ migration نباید مقدار، شخص، واحد یا تاریخ را حدس بزند.
6. migration دوباره روی clone اجرا شود تا idempotency اثبات شود.
7. گزارش before/after و اختلاف تهیه شود.

### کنترل‌های تطبیق اجباری

| حوزه | کنترل |
|---|---|
| پول | جمع مبلغ هر نوع سند، جمع بدهکار/بستانکار و جمع cash movement |
| کالا | مقدار و ارزش هر کالا، تعداد گردش‌ها، موجودی منفی و صفر |
| اشخاص | ماندهٔ هر شخص، دریافت/پرداخت و اسناد تخصیص‌نیافته |
| صندوق/بانک | ماندهٔ هر حساب و مجموع انتقال‌های داخلی |
| اسناد | شمارش بر اساس نوع/وضعیت و حفظ شناسهٔ سند قدیمی |
| ممیزی | exceptionها، رکوردهای ردشده و mappingهای دستی |
| ساختار | foreign key، index، trigger و schema version |

اختلاف باید به تفکیک سند/کالا/شخص گزارش شود؛ برابری صرف جمع کل برای پذیرش کافی نیست.

## ۶. معیار Go / No-Go

**Go فقط وقتی مجاز است که:**

- تمام پیش‌شرط‌های بخش ۲ برقرار باشند.
- هیچ اختلاف حل‌نشده در حساب‌های کنترلی باقی نمانده باشد.
- تمام golden scenarioهای مصوب پاس شده باشند.
- exceptionها صفر یا تک‌تک با تصمیم مالک تعیین تکلیف شده باشند.
- اجرای دوم migration رکورد تکراری ایجاد نکرده باشد.
- restore drill موفق و زمان بازیابی ثبت شده باشد.
- مالک کسب‌وکار و مسئول فنی هر دو cutover را تأیید کرده باشند.

**No-Go / توقف فوری:**

- اختلاف حل‌نشدهٔ ارزش یا مقدار حتی برای یک کالا.
- اختلاف ماندهٔ یک شخص یا حساب نقد/بانک.
- orphan FK یا شکست integrity check.
- عدم تطبیق اسناد منبع و مقصد.
- تست شکست‌خورده یا CI ناموفق روی SHA مقصد.
- امکان نوشتن هم‌زمان نسخهٔ قدیم و جدید.
- backup بدون restore اثبات‌شده.

## ۷. Cutover کنترل‌شده

1. پنجرهٔ نگهداری اعلام و ورود نوشتن در نسخهٔ قدیمی متوقف شود.
2. آخرین backup سازگار تهیه و checksum ثبت شود.
3. preflight نهایی و snapshot جمع‌های کنترلی گرفته شود.
4. migration نهایی روی target خالی اجرا شود؛ نتیجه با shadow پذیرفته‌شده مقایسه شود.
5. کنترل‌های integrity و تمام تطبیق‌ها اجرا شوند.
6. فقط پس از تأیید دوگانه، مسیر دیتابیس مقصد فعال شود.
7. smoke test محدود و غیرمخرب انجام شود؛ ثبت آزمایشی فقط در محیط تست، نه در دفتر واقعی.
8. دسترسی نوشتن باز شود و زمان، commit، schema version و مسئول تأیید ثبت شود.
9. نسخهٔ قدیمی و backup تا پایان دورهٔ پایش نگهداری شوند.

**ممنوع:** اجرای هم‌زمان نسخهٔ قدیم و جدید روی یک دیتابیس یا replay دوبارهٔ اسناد عملیاتی بدون idempotency و کنترل source reference.

## ۸. پایش پس از Cutover

در اولین بازهٔ کاری و پایان روز:

- جمع موجودی مقداری/ارزشی و موارد منفی کنترل شود.
- ماندهٔ اشخاص و حساب‌های نقد/بانک با snapshot قبل مقایسه شود.
- تعداد و جمع postingها به تفکیک source بررسی شود.
- خطاهای migration، constraint و audit مرور شود.
- گزارش سود و بهای تمام‌شده برای اسناد نمونه با محاسبهٔ مستقل تطبیق داده شود.
- backup جدید تهیه و restore آزمایشی زمان‌بندی شود.

هر اختلاف مالی حل‌نشده، محرک توقف نوشتن و ارزیابی rollback است.

## ۹. Rollback

1. نوشتن برنامه متوقف و زمان توقف ثبت شود.
2. از دیتابیس جدید snapshot forensic تهیه شود؛ آن را حذف یا overwrite نکن.
3. مشخص شود پس از cutover سند واقعی ثبت شده است یا خیر.
4. اگر هیچ سند واقعی پس از cutover ثبت نشده، مسیر دیتابیس به backup قبلیِ restore-verified برگردد.
5. اگر سند واقعی ثبت شده، بازگشت ساده به backup ممنوع است؛ ابتدا رویدادهای پس از cutover با شناسه و checksum استخراج و اثرشان تعیین تکلیف شود. سپس برنامهٔ بازگشت/forward-fix با تأیید مالک نوشته شود.
6. پس از بازگشت، integrity/FK check و جمع‌های کنترلی اجرا شود.
7. علت، بازهٔ زمانی، اسناد متأثر و اقدام اصلاحی ثبت شود.

**قاعده:** برای rollback، migration معکوس حدسی روی دادهٔ زنده اجرا نکن. در صورت ابهام، سیستم در حالت maintenance باقی بماند.

## ۱۰. شواهد و ثبت عملیات

برای هر اجرای migration پرونده‌ای مستقل نگهداری شود:

- شناسهٔ عملیات و محیط
- commit SHA و schema/migration version
- زمان شروع/پایان و مسئولان
- checksum و محل امن backup
- خروجی integrity/FK checks
- snapshot جمع‌های کنترلی قبل/بعد
- گزارش shadow و exceptionها
- خروجی golden/integration tests
- تصمیم Go/No-Go و تأییدکنندگان
- گزارش smoke test و پایش
- در صورت rollback، علت و شواهد قبل/بعد

token، password و دادهٔ شخصی مشتری در گزارش مخزن ثبت نشود؛ فقط شناسه‌های تست یا دادهٔ ناشناس‌شده استفاده شود.

## ۱۱. موارد خارج از اختیار این سند

این runbook مجوز موارد زیر نیست:

- تغییر سیاست‌های DEC-01 تا DEC-10
- اجرای migration روی دیتابیس واقعی
- تغییر schema یا کد اجرایی
- فعال‌کردن نسخهٔ جدید برای کاربران
- حذف backup یا دیتابیس قدیمی
- merge کردن PR یا تغییر شاخهٔ main

## ۱۲. معیار تکمیل آمادگی عملیاتی

این سند زمانی از «طراحی» به «آمادهٔ اجرا» ارتقا می‌یابد که سیاست‌ها تصویب، migration پیاده‌سازی، تست‌ها روی SHA نهایی سبز، restore drill مستند و checklist با شواهد واقعی تکمیل شده باشد. تا آن زمان وضعیت این runbook **Ready for Review / Not Authorized for Production Execution** است.
