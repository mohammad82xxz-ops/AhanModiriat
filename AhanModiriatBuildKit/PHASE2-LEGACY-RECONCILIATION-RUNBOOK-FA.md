# دستورالعمل ممیزی و تطبیق داده‌های قدیمی انبار (Legacy Reconciliation Runbook)

> وضعیت: **طرح اجراییِ فقط‌خواندنی برای کپی ایزوله**
>
> این سند مجوز اتصال به دیتابیس عملیاتی، تغییر داده، اجرای migration یا اصلاح خودکار نیست.
> هیچ فایل دیتابیس واقعی در این بررسی در دسترس نبوده است؛ بنابراین هیچ مقدار واقعی، فهرست واحد یا نرخ خطایی در این سند ادعا نمی‌شود.

## ۱. هدف

پیش از طراحی migration فاز ۲ باید مشخص شود داده‌های قدیمی هر محصول و هر سند چه معنایی دارند. خروجی این دستورالعمل یک گزارش قابل ممیزی است که:

- واحدهای واقعی ثبت‌شده را بدون normalize یا بازنویسی فهرست کند؛
- معنای مقدار هر جدول را بر اساس مسیر ثبت سند حفظ کند؛
- داده‌های ناقص، ناسازگار، مبهم و خارج از دامنهٔ تبدیل را به exception تبدیل کند؛
- موجودی فعلی را با گردش‌های قابل بازسازی مقایسه کند، بدون اینکه baseline را افتتاحیهٔ تاریخ‌دار فرض کند؛
- ورودی لازم برای طراحی migration آزمایشی را فراهم کند.

## ۲. ممنوعیت‌ها و پیش‌شرط‌ها

### ممنوع

- اتصال این runbook به فایل دیتابیس فعال کسب‌وکار.
- اجرای `UPDATE`، `DELETE`، `INSERT`، `ALTER`، `VACUUM` یا migration روی منبع.
- تغییر نام/فاصله/حروف واحدها برای «تمیزکردن» داده در مرحلهٔ استخراج.
- تبدیل واحد بر اساس نام کالا، category، وزن تئوریک یا حدس کاربر.
- فرض اینکه `products.stock` یا baseline کارت گردش یک سند افتتاحیهٔ رسمی است.
- حذف، گردکردن یا صفرکردن مقدارهای منفی، خالی یا غیرعادی.

### پیش‌شرط

1. مالک کسب‌وکار یک backup قابل بازیابی و مجاز برای ممیزی فراهم کند.
2. از backup یک کپی جداگانه ساخته شود؛ checksum فایل منبع و کپی ثبت شود.
3. ممیزی روی کپی انجام شود و فایل منبع فقط read-only باز شود.
4. نسخهٔ برنامه، schema version، تاریخ تهیهٔ backup و timezone نامعلوم/معلوم ثبت شود.
5. اگر backup رمزگذاری‌شده، ناقص یا ناسازگار است، ممیزی متوقف و exception ثبت شود.

## ۳. ثبت هویت منبع و زنجیرهٔ نگهداری

برای هر اجرای ممیزی، سربرگ گزارش باید شامل این فیلدها باشد:

| فیلد | توضیح |
|---|---|
| audit_run_id | شناسهٔ یکتای اجرای ممیزی |
| source_label | نام مستعار منبع؛ بدون افشای مسیر شخصی |
| source_sha256 | SHA-256 فایل backup منبع |
| working_copy_sha256 | SHA-256 کپی کاری قبل از ممیزی |
| app_commit | commit دقیق نسخهٔ برنامه |
| schema_fingerprint | فهرست جدول/ستون/نوع از sqlite_master و table_info |
| started_at_utc | زمان اجرای ممیزی UTC |
| operator | شناسهٔ مسئول مجاز |
| mode | باید `READ_ONLY` باشد |
| result | complete / partial / blocked |
| notes | محدودیت‌ها و هشدارها |

اگر checksum کپی کاری پس از ممیزی تغییر کرده باشد، گزارش قابل قبول نیست تا علت تغییر روشن شود.

## ۴. بازکردن امن SQLite

الگوی اجرایی باید از URI حالت read-only استفاده کند و روی connection، `PRAGMA query_only=ON` فعال شود. نمونهٔ مفهومی:

```python
import sqlite3
from pathlib import Path

db_path = Path("isolated-copy.sqlite").resolve()
uri = db_path.as_uri() + "?mode=ro"
con = sqlite3.connect(uri, uri=True)
con.row_factory = sqlite3.Row
con.execute("PRAGMA query_only = ON")
assert con.execute("PRAGMA query_only").fetchone()[0] == 1
```

نکته: این قطعه نمونهٔ روش اتصال است، نه اسکریپت آمادهٔ اجرا روی هر فایل. مسیر باید به کپی ایزوله اشاره کند. از فعال‌کردن `immutable=1` فقط وقتی استفاده شود که فایل واقعاً snapshot ثابت باشد و WAL/sidecarهای لازم قبلاً به‌شکل معتبر checkpoint شده باشند؛ در غیر این صورت ممکن است آخرین داده‌ها دیده نشوند.

ابتدای هر run این بررسی‌ها انجام شوند:

- `PRAGMA integrity_check`؛ نتیجه باید `ok` باشد.
- `PRAGMA foreign_key_check`؛ تمام ردیف‌های خروجی ثبت شوند.
- وجود جدول‌ها و ستون‌های مورد انتظار؛ schema متفاوت به‌جای حدس‌زدن mapping، گزارش را partial/blocked کند.
- شمارش رکورد هر جدول قبل از شروع استخراج.

## ۵. فرهنگ معنای داده (Data Semantics)

| جدول/فیلد | معنای فعلی شناخته‌شده | واحد/قاعدهٔ استخراج |
|---|---|---|
| `products.stock` | ماندهٔ فعلی موجودی | `products.unit`؛ واحد پایهٔ تعریف‌شده در محصول |
| `products.min_stock` | حداقل موجودی | طبق قرارداد فعلی واحد پایه؛ برچسب در UI همیشه روشن نیست |
| `products.purchase_unit` | واحد ورود خرید | متن خام؛ alias خودکار ممنوع |
| `products.purchase_factor` | ضریب تبدیل واحد خرید به واحد پایه | مقدار خام؛ اعتبار و معنای آن جداگانه بررسی شود |
| `products.sale_unit` | واحد ورودی فروش | متن خام |
| `products.sale_factor` | ضریب تبدیل واحد فروش به واحد پایه | مقدار خام؛ با purchase_factor جایگزین نشود |
| `purchases.qty` | مقدار ثبت‌شده در واحد خرید | برای بازسازی اثر موجودی، ضریب خرید همان محصول لازم است؛ snapshot تاریخی factor فعلاً تضمین نشده |
| `sales.qty` | مقدار ذخیره‌شده در واحد پایه | sale_factor دوباره اعمال نشود |
| `purchase_returns.qty` | مقدار مرجوعی خرید در واحد پایه | ضریب خرید دوباره اعمال نشود |
| `sales_returns.qty` | مقدار مرجوعی فروش در واحد پایه | ضریب فروش دوباره اعمال نشود |
| `inventory_adjustments.expected_qty/count-ed_qty/delta_qty` | مقدارهای شمارش/اختلاف در واحد پایه | اختلاف باید با delta سازگار باشد؛ سیاست ارزش‌گذاری خارج از دامنه است |

**محدودیت تاریخی:** چون ضریب و واحد در محصول فعلی نگهداری می‌شوند و snapshot تاریخی آن‌ها در تمام اسناد قدیمی تضمین نشده است، استفاده از factor فعلی برای تفسیر یک خرید قدیمی فقط یک فرض بازسازی است. این فرض باید در گزارش با برچسب `CURRENT_PRODUCT_FACTOR_ASSUMED` مشخص شود و نباید به‌عنوان واقعیت تاریخی قطعی ارائه شود.

## ۶. مجموعه استخراج‌های اجباری

تمام خروجی‌ها باید هم aggregate و هم ردیف خام قابل ردیابی داشته باشند. queryها باید بعد از تطبیق schema با کپی اجرا شوند؛ در صورت نبود ستون، query اصلاح حدسی نشود.

### ۶.۱ شمارش و واحدهای خام محصول

گزارش aggregate برای `unit`، `purchase_unit` و `sale_unit`:

- مقدار خام دقیق (شامل فاصله و تفاوت نوشتاری)؛
- تعداد محصول؛
- تعداد محصول فعال/غیرفعال، فقط اگر فیلد متناظر در schema واقعاً وجود داشته باشد؛
- شناسه‌های محصول؛
- تعداد مقدار خالی/NULL.

برای هر محصول نیز این ستون‌ها استخراج شوند:
`id, name, code, category, unit, stock, min_stock, purchase_unit, purchase_factor, sale_unit, sale_factor, roll_weight, sheet_area`.

نام/کد محصول می‌تواند دادهٔ حساس تجاری باشد؛ گزارش قابل اشتراک باید شناسه‌های ناشناس داشته باشد و نسخهٔ کامل فقط در دسترس مالک مجاز بماند.

### ۶.۲ ضرایب و پارامترهای فیزیکی

برای هر محصول این موارد علامت‌گذاری شوند:

- factor برابر صفر یا منفی؛
- factor تهی یا ناسازگار با schema؛
- factor غیرمتناهی یا خارج از دامنهٔ عددی امن؛
- `purchase_unit` یا `sale_unit` خالی؛
- واحدهای متنی متفاوت که شاید alias باشند، بدون ادغام خودکار؛
- `roll_weight` یا `sheet_area` منفی، صفر، غیرمتناهی یا دارای واحد/معنای نامشخص؛
- `stock` یا `min_stock` منفی و مقدارهای بسیار بزرگ.

مقادیر صفر `roll_weight` و `sheet_area` به‌تنهایی ثابت نمی‌کنند که وزن یا مساحت واقعی صفر است؛ ممکن است به معنای ثبت‌نشدن باشند. گزارش باید بین zero و unknown فقط وقتی schema/ورودی چنین تمایزی دارد فرق بگذارد؛ در غیر این صورت وضعیت را `AMBIGUOUS_ZERO_OR_UNKNOWN` ثبت کند.

### ۶.۳ مقدارهای سند

برای هر جدول، count، min، max، sum و تعداد مقدارهای منفی/صفر/NULL گزارش شود؛ اما معنای مقدار در همان جدول حفظ شود:

- purchases.qty: واحد خرید؛
- sales.qty: واحد پایه؛
- purchase_returns.qty و sales_returns.qty: واحد پایه؛
- inventory_adjustments: واحد پایه.

جمع این ستون‌ها در یک total مشترک ممنوع است. اگر برای تحلیل مقدار پایهٔ خرید از `qty × current purchase_factor` استفاده شد، خروجی باید در ستون مشتق‌شدهٔ جدا با نام روشن ذخیره شود و فرض factor فعلی همراه آن باشد.

### ۶.۴ تطبیق گردش و مانده

برای هر محصول:

1. اثر خرید پایه را با factor فعلی فقط به‌عنوان بازسازی مشروط محاسبه کن.
2. اثر فروش پایه را از `sales.qty` بخوان.
3. اثر مرجوعی خرید و فروش را در واحد پایه و با علامت صحیح مسیر کد لحاظ کن.
4. تعدیل‌های انبار را از `delta_qty` بخوان.
5. مقدار `baseline = current_stock - total_delta` را فقط به‌عنوان baseline حسابی گردش‌های موجود گزارش کن.
6. baseline را بدون سند/تاریخ/تأیید به موجودی افتتاحیه تبدیل نکن.

اگر اثر حذف/ویرایش اسناد قدیمی، snapshot ضریب یا ledger کامل در دسترس نیست، اختلاف را `UNRECONCILED` گزارش کن؛ مانده را با تغییر خودکار همسان نکن.

## ۷. طبقه‌بندی Exception

هر exception باید دارای severity، code، جدول، record_id، product_id، مقدار خام، فرض لازم، دلیل، اقدام بعدی و owner باشد.

| کد | شرط نمونه | شدت پیش‌فرض | اقدام |
|---|---|---|---|
| UNIT-001 | واحد پایه خالی/NULL | blocker | تعیین واحد از سند معتبر؛ بدون حدس |
| UNIT-002 | واحد خرید/فروش خالی | high | بررسی سند و تنظیمات محصول |
| UNIT-003 | واحد ناشناخته یا alias محتمل | high | mapping تأییدشدهٔ مالک |
| FACTOR-001 | factor صفر/منفی | blocker | توقف تبدیل همان محصول |
| FACTOR-002 | factor غیرمتناهی/خارج از دامنه | blocker | بررسی منبع مقدار |
| FACTOR-003 | ضریب فعلی برای سند تاریخی فاقد snapshot | high | علامت‌گذاری فرض؛ تأیید مستند |
| QTY-001 | مقدار منفی در مسیر فاقد معنای برگشت | high | بررسی سند/اصلاحیه؛ حفظ خام |
| QTY-002 | مقدار غیرمتناهی/overflow/NULL غیرمنتظره | blocker | توقف ردیف/محصول |
| QTY-003 | مقدار کمتر از دقت هدف یا دارای اعشار مبهم | high | انتظار تصمیم دقت/گردکردن |
| PHYS-001 | وزن تئوریک موجود، وزن واقعی ناموجود | medium | وزن واقعی unknown باقی بماند |
| PHYS-002 | تعداد و وزن به‌اشتباه از یکدیگر استنتاج شده | blocker | بازسازی از سند معتبر |
| LEDGER-001 | مانده با گردش قابل بازسازی تطبیق ندارد | blocker | بررسی ledger و baseline |
| LEDGER-002 | baseline فاقد سند افتتاحیه | high | افتتاحیهٔ تأییدشده لازم است |
| REL-001 | رابطهٔ سند/محصول orphan یا ناسازگار | blocker | بررسی مرجع؛ اتصال حدسی ممنوع |
| DATE-001 | تاریخ سند نامعتبر یا مبهم | high | بررسی سند اصلی؛ تبدیل حدسی ممنوع |

شدت‌ها صرفاً سطح کنترل ممیزی‌اند و به معنی حذف یا اصلاح خودکار رکورد نیستند.

## ۸. قالب گزارش خروجی

حداقل فایل‌های خروجی:

1. `audit_manifest.json`: metadata، checksum و schema fingerprint.
2. `product_unit_inventory.csv`: یک ردیف برای هر محصول، با واحدها و factorهای خام.
3. `unit_value_counts.csv`: مقادیر متمایز خام و تعداد استفاده.
4. `document_quantity_profile.csv`: count/min/max/sum و کیفیت مقدار برای هر جدول.
5. `product_reconciliation.csv`: current stock، اجزای گردش، baseline و اختلاف.
6. `exceptions.csv`: فهرست استثناها با شناسه و علت.
7. `audit_summary.md`: تعداد محصولات، تعداد اسناد، تعداد exception بر اساس code/severity، محدودیت‌ها و نتیجه.
8. `checksums.txt`: checksum همهٔ خروجی‌ها.

فایل CSV باید UTF-8، header ثابت، decimal separator استاندارد و بدون فرمت نمایشی محلی باشد. مقدار خام نباید با مقدار canonical مشتق‌شده در یک ستون مخلوط شود.

## ۹. گیت‌های تصمیم و پذیرش

### پیش از mapping واحد

- ۱۰۰٪ محصولات باید واحد پایهٔ شناخته‌شده یا exception blocker داشته باشند.
- هر alias پیشنهادی باید با نمونهٔ واقعی و تأیید مالک همراه باشد.
- factorهای خرید و فروش جداگانه بررسی شوند.
- ابعاد جرم/تعداد/طول/مساحت با هم قابل تبدیل فرض نشوند.

### پیش از migration آزمایشی

- همهٔ exceptionهای blocker تعیین تکلیف مستند داشته باشند.
- فرض factor تاریخی یا به snapshot مستند تبدیل شود یا migration آن ردیف متوقف بماند.
- totalهای قبل/بعد برای هر گروه معنایی قابل تطبیق باشند.
- اجرای دوم روی fixture خروجی یکسان بدهد.
- rollback و بازیابی از backup روی fixture اثبات شود.
- هیچ مقدار ناشناخته به صفر یا default تبدیل نشود.

### پیش از هر migration عملیاتی

این PR یا این runbook به‌تنهایی کافی نیست. migration عملیاتی به تأیید مستقل مالک، backup قابل بازیابی، rehearsal روی کپی، گزارش اختلاف امضاشده و PR اجرایی جدا نیاز دارد. اجرای migration عملیاتی در محدودهٔ این پروژه و این PR انجام نمی‌شود.
