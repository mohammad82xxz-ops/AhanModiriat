# قرارداد قالب XLSX نسخه‌دار و پیش‌نمایش Import (Q2-B)

> وضعیت: **طراحی؛ بدون تغییر کد import/export**
>
> هدف، مشخص‌کردن قرارداد فایل و رفتار preview است. تا تصویب و پیاده‌سازی در PR اجرایی جدا، قالب فعلی برنامه همان رفتار موجود را دارد. این سند مجوز تغییر داده یا import روی دیتابیس واقعی نیست.

## ۱. مسئله و هدف

قالب فعلی محصولات، واحد و ضرایب را به‌صورت ستون‌های متنی/عددی حمل می‌کند؛ اما خود فایل قرارداد قابل اتکایی دربارهٔ نسخهٔ schema، معنای واحد پایه، جهت ضریب یا رفتار واحد ناشناخته ارائه نمی‌دهد. import نیز نباید صرفاً به دلیل قابل‌خواندن بودن یک رشته، آن را واحد معتبر تلقی کند.

قالب جدید باید:

- نسخهٔ قالب و نسخهٔ قرارداد واحد را آشکار کند؛
- مقدار خام ورودی را از مقدار canonical/مشتق‌شده جدا نگه دارد؛
- واحدهای ناشناخته و aliasهای تأییدنشده را به exception تبدیل کند؛
- پیش از هر write، preview و خلاصهٔ اثر را نشان دهد؛
- خطاهای سطر و فایل را با شناسهٔ پایدار گزارش کند؛
- import تکراری و retry را قابل کنترل کند.

## ۲. ساختار Workbook پیشنهادی

| Sheet | نقش | الزامات |
|---|---|---|
| `_manifest` | نسخه و metadata قالب | اجباری، یک ردیف metadata با key/value |
| `Guide` | راهنمای کاربر | واحد پایه، معنای factorها، مثال و هشدارها |
| `Products` | دادهٔ کالا | ستون‌های تعریف‌شده و header ثابت |
| `People` | اشخاص | ساختار فعلی، مستقل از قرارداد مقدار |
| `_lists` | واژگان مجاز و شناسه‌های enum | مخفی‌کردن بصری مجاز است، حذف اطلاعات ممنوع |

نام sheetها و headerها شناسهٔ ماشینی‌اند؛ ترجمهٔ متن نمایشی در Guide مجاز است اما تغییر header بدون افزایش نسخهٔ schema ممنوع است.

### ۲.۱ metadata الزامی

Sheet `_manifest` باید حداقل این کلیدها را داشته باشد:

| key | معنی |
|---|---|
| `template_id` | شناسهٔ ثابت قالب، مثلاً `ahan.products` |
| `template_version` | نسخهٔ قالب، مانند `1.0.0` |
| `schema_version` | نسخهٔ ساختار ستون‌ها |
| `quantity_contract_version` | نسخهٔ قرارداد معنای واحد و مقدار |
| `exported_at` | زمان export با قالب ISO-8601 و offset مشخص |
| `application_version` | نسخهٔ برنامهٔ صادرکننده |
| `source_instance_id` | شناسهٔ غیرحساس نصب/منبع، در صورت وجود |
| `locale_hint` | راهنمای زبان/نمایش؛ نه مبنای parse عدد |
| `decimal_convention` | قرارداد عددی فایل، ترجیحاً decimal point و بدون جداکنندهٔ هزارگان |

نبودن `template_id` یا نسخهٔ ناسازگار نباید با حدس بر اساس نام فایل جبران شود.

### ۲.۲ ستون‌های Products

نسخهٔ اول قالب باید ستون‌های فعلی را با معنای روشن حفظ کند:

| ستون | نوع منطقی | معنای فایل |
|---|---|---|
| `external_key` | text | شناسهٔ پایدار برای تطبیق؛ اگر موجود نیست خالی |
| `name` | text | نام کالا |
| `code` | text | کد کالا |
| `category` | text/enum | دستهٔ کالا؛ mapping فقط با فهرست مصوب |
| `base_unit_code` | enum/text | کد واحد پایهٔ محصول |
| `stock_legacy_raw` | decimal text | مقدار ماندهٔ قدیمی، بدون ادعای canonical |
| `min_stock_legacy_raw` | decimal text | حداقل موجودی قدیمی |
| `purchase_unit_raw` | text | واحد خرید خام |
| `purchase_factor_raw` | decimal text | ضریب خرید خام |
| `sale_unit_raw` | text | واحد فروش خام |
| `sale_factor_raw` | decimal text | ضریب فروش خام |
| `roll_weight_legacy_raw` | decimal text | مقدار قدیمی وزن رول؛ semantics تأییدنشده |
| `sheet_area_legacy_raw` | decimal text | مقدار قدیمی مساحت ورق؛ semantics تأییدنشده |
| `notes` | text | توضیحات |

در export سازگار با نسخهٔ فعلی می‌توان headerهای legacy را حفظ کرد، اما manifest و Guide باید معنای آن‌ها را تعریف کنند. تغییر headerها فقط در major schema version مجاز است.

**مهم:** ستون `stock_legacy_raw` در فایل مهاجرت نباید به‌عنوان موجودی canonical گرم/تعداد معرفی شود. معنای آن به واحد پایهٔ خام و وضعیت دادهٔ قدیمی وابسته است. مقدار canonical پیشنهادی باید در preview و گزارش جداگانه محاسبه شود، نه اینکه بی‌صدا جای مقدار خام قرار گیرد.

## ۳. قرارداد واحدها و واژگان

1. واژه‌نامهٔ واحدها باید کد پایدار، نام نمایشی فارسی، dimension و factor مرجع نسخه‌دار داشته باشد.
2. dimensionها حداقل جرم، تعداد، طول، مساحت و واحد بسته‌بندیِ تعریف‌شده توسط کسب‌وکار را از هم جدا کنند.
3. تبدیل بین dimension ناسازگار ممنوع باشد.
4. متن خام واحد در فایل حفظ شود؛ normalize صرفاً برای lookup و بدون overwrite مقدار خام انجام شود.
5. alias تنها وقتی پذیرفته شود که mapping آن در registry نسخه‌دار و به تأیید مالک رسیده باشد.
6. نام‌های آزاد مانند «بندیل»، «شاخه»، «بسته» یا اختصارات محلی بدون تعریف دقیق، به‌صورت خودکار هم‌معنی فرض نشوند.
7. `purchase_factor` جهت تبدیل واحد خرید به واحد پایه و `sale_factor` جهت تبدیل واحد فروش به واحد پایه را دارد؛ این دو مستقل‌اند.
8. ضریب موجود در فایل legacy snapshot تاریخی یک سند را اثبات نمی‌کند.

## ۴. جریان Import: Parse → Validate → Preview → Commit

<escape>
[فایل انتخاب می‌شود]
        |
        v

        |
        v
[Parse خام؛ بدون نوشتن]
        |
        v
[اعتبارسنجی ساختار، واحد، factor و کلیدها]
        |
        v
[ساخت preview و exception report]
        |
        +---- خطای blocker؟ ---- بله ---> [Commit ممنوع]
        |
        خیر
        |
        v
[تأیید صریح کاربر و انتخاب سیاست conflict]
        |
        v

        |
        v
[گزارش نتیجه + audit reference]
</escape>

هیچ ردیفی پیش از پایان preview نباید در دیتابیس نوشته شود. انتخاب فایل یا نمایش preview به معنی تأیید import نیست.

### ۴.۱ مراحل parse

- سقف اندازهٔ فایل فشرده و اندازهٔ بازشدهٔ XML اعمال شود.
- تعداد sheet، تعداد ردیف/ستون، نوع فایل و ساختار ZIP کنترل شود.
- فرمول‌های Excel به‌عنوان مقدار ورودی قابل اعتماد پذیرفته نشوند؛ فقط cached value قابل parse است یا سلول فرمول‌دار به exception تبدیل شود.
- سلول‌های hidden، merged، external link و macro نباید مسیر دورزدن validation ایجاد کنند.
- رشته‌ها trim یا normalize مخرب نشوند؛ مقدار خام و مقدار parseشده جدا بمانند.
- عددهای NaN، Infinity، overflow، رشتهٔ خالی در فیلد الزامی و فرمت عددی مبهم رد شوند.
- parser عدد باید مستقل از locale سیستم باشد؛ `1,25` نباید در یک سیستم 1.25 و در سیستم دیگر 125 یا 1250 تفسیر شود.

### ۴.۲ طبقه‌بندی validation

| severity | معنا | اجازهٔ Commit |
|---|---|---|
| blocker | ساختار نامعتبر، واحد پایهٔ ناشناخته، factor نامعتبر، کلید تکراری مبهم یا مقدار غیرقابل parse | خیر |
| error | ردیف قابل تفسیر نیست یا تعارض حل‌نشده دارد | خیر برای ردیف؛ حالت کلی فقط طبق سیاست اتمیک |
| warning | مقدار legacy مبهم است اما خام قابل حفظ است | فقط با سیاست صریح و تأیید کاربر |
| info | تبدیل/تطبیق بدون ابهام انجام شده | بله پس از تأیید |

هیچ warning نباید بی‌صدا به مقدار صفر، واحد پیش‌فرض یا factor=1 تبدیل شود.

## ۵. قرارداد Preview

Preview باید قبل از commit این اطلاعات را نشان دهد:

### خلاصهٔ کل فایل

- نام و checksum فایل؛
- template/schema/quantity contract version؛
- تعداد sheetها و ردیف‌های خوانده‌شده؛
- تعداد ردیف‌های جدید، قابل تطبیق، بدون تغییر، متعارض و ردشده؛
- تعداد blocker/error/warning/info؛
- تعداد واحدهای شناخته‌شده، aliasهای تأییدشده و واحدهای ناشناخته؛
- هشدار دربارهٔ داده‌های legacy که به canonical تبدیل قطعی نشده‌اند.

### جزئیات هر ردیف

- sheet و شمارهٔ ردیف؛
- external_key و شناسهٔ محصول مقصد، اگر قابل تعیین است؛
- فیلد؛
- مقدار خام؛
- مقدار parseشده؛
- واحد خام و dimension مورد انتظار؛
- factor خام و منبع آن؛
- مقدار canonical پیشنهادی، در صورت امکان؛
- وضعیت و کد exception؛
- اقدام پیشنهادی و اینکه آیا نیازمند تصمیم مالک است.

### کنترل‌های تأیید

- انتخاب رفتار تعارض (رد، skip، update) باید صریح باشد و پیش‌فرض update مخرب نباشد.
- اگر فایل دارای blocker است، دکمه/مسیر commit در دسترس نباشد.
- تأیید preview به همان checksum و همان نتیجهٔ parse مقید باشد؛ تغییر فایل، نسخهٔ قالب یا دادهٔ مقصد preview را منقضی کند.
- خلاصهٔ قبل از commit و نتیجهٔ پس از commit قابل دانلود باشد.

## ۶. تطبیق و جلوگیری از تکرار

ترتیب تطبیق پیشنهادی:

1. `external_key` پایدار و معتبر؛
2. شناسهٔ داخلی فقط برای round-trip همان نصب و با بررسی مالکیت؛
3. کد کالا در صورت unique بودن و تأیید سیاست؛
4. نام کالا به‌تنهایی هرگز کلید قطعی تطبیق نیست.

اگر چند ردیف به یک محصول یا یک ردیف به چند محصول بخورد، وضعیت conflict است؛ fuzzy match فقط پیشنهاد کمکی در preview است و commit خودکار نمی‌کند.

برای retry و idempotency، سیستم باید checksum فایل، template version، انتخاب‌های preview و نتیجهٔ import را در یک import batch ثبت کند. اجرای دوبارهٔ batch موفق نباید دوباره سند/محصول ایجاد کند. این batch metadata نباید جای audit log رویدادهای تجاری را بگیرد.

## ۷. تراکنش و خطا

- در حالت پیش‌فرض، commit باید اتمیک باشد: تمام ردیف‌های پذیرفته‌شده در یک transaction و rollback کامل در شکست.
- اگر حجم فایل به batch چندمرحله‌ای نیاز دارد، این رفتار باید قرارداد مستقل با checkpoint، وضعیت قابل ادامه و گزارش دقیق داشته باشد؛ partial import بدون اعلام صریح ممنوع است.
- خطای DB پس از preview نباید به success ظاهری تبدیل شود.
- گزارش commit باید تعداد واقعی insert/update/skip/reject و شناسهٔ batch را اعلام کند.
- هیچ تغییر stock یا گردش انبار از صرف import مشخصات کالا استنتاج نشود، مگر اینکه workflow جدا و صریح برای سند افتتاحیه/تعدیل تعریف و تأیید شده باشد.

## ۸. Export و round-trip

- export باید manifest و Guide داشته باشد.
- export → import بدون تغییر باید داده‌های پشتیبانی‌شده را از نظر معنایی حفظ کند.
- round-trip نباید شناسه‌ها، واحد خام، factor خام یا دقت عددی را بی‌صدا تغییر دهد.
- مقادیر نمایشی locale-specific فقط در UI نمایش داده شوند؛ فایل machine-readable قرارداد عددی ثابت داشته باشد.
- export باید version و checksum در manifest یا metadata گزارش خروجی داشته باشد.
- ستون‌های جدید در minor version فقط با سازگاری backward روشن اضافه شوند؛ حذف/تغییر معنای ستون major version می‌خواهد.

## ۱۰. ارتباط با رفتار فعلی و سازگاری

- قالب فعلی export محصولات ستون‌های `unit`، `stock`، `min_stock`، `purchase_unit`، `purchase_factor`، `sale_unit`، `sale_factor`، `roll_weight` و `sheet_area` دارد.
- قالب فعلی import نام واحد را به‌صورت متن می‌پذیرد و registry/preview نسخه‌دار ندارد.
- این سند رفتار فعلی را تغییر نمی‌دهد و نباید به‌عنوان تضمین قابلیت import نسخهٔ جدید در build جاری تعبیر شود.
- مهاجرت از قالب قدیمی باید از طریق parser نسخهٔ legacy و preview انجام شود؛ فایل قدیمی نباید به‌صورت خودکار به قالب جدید rewrite شود.
- CSV مالی فعلی جایگزین XLSX مهاجرت کالا نیست.
