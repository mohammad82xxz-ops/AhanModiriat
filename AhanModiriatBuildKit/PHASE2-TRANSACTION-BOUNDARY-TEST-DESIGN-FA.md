## ۱. یافته‌های قطعی از مسیر کد

### ۱.۱ مرز تراکنش POST

در `Handler.do_POST`، مسیرهای مالی پس از اعتبارسنجی درخواست، در بلوک زیر اجرا می‌شوند:

```python
with LOCK, conn() as c:
    # consume form token
    # execute route mutation
    # insert audit_log
```

در پیاده‌سازی فعلی:

- `LOCK` یک قفل سراسری درون همان process است؛ درخواست‌های POST این process را سریالی می‌کند.
- `conn()` یک اتصال SQLite می‌سازد و `with conn() as c` مرز commit/rollback تراکنش را فراهم می‌کند.
- استثناهای عملیات پس از خروج از بلوک تراکنش، در `except` بیرونی گرفته و به پیام redirect تبدیل می‌شوند.
- مصرف `form_submission_tokens`، درج سند، درج/حذف cash mirror و درج `audit_log` همگی در همان بلوک تراکنش انجام می‌شوند.

بنابراین شکست تزریق‌شده در `sync_cash_posting` برای یک route، باید کل تغییرات همان درخواست را rollback کند؛ از جمله مصرف token، ایجاد شخص جدید و سند مالی. این انتظار باید با تست واقعی اثبات شود، نه صرفاً از روی ساختار کد مفروض گرفته شود.

**محدودیت مهم:** `LOCK` فقط در یک process مشترک است. این کد به‌تنهایی تضمین هم‌زمانی چند process مستقل را اثبات نمی‌کند. تست thread در یک server فقط رفتار تک‌process را می‌سنجد و نباید به‌عنوان اثبات ایمنی چندپردازه گزارش شود.

### ۱.۲ ثبت تسویه و mirror نقدی

در شاخه `add_settlement` در `app.py`:

1. نام طرف‌حساب normalize می‌شود.
2. `ensure_person` شخص را ایجاد یا بازیابی می‌کند.
3. تاریخ و مبلغ اعتبارسنجی می‌شوند.
4. ردیف `settlements` درج می‌شود.
5. `person_id` روی ردیف تسویه ثبت می‌شود.
6. `sync_cash_posting` با جهت دریافت/پرداخت اجرا می‌شود.
7. در ادامه، رویداد `audit_log` درج می‌شود.

در `sync_cash_posting` ابتدا mirrorهای قبلی همان `source_table/source_id` حذف می‌شوند؛ مبلغ به واحد صحیح مالی تبدیل می‌شود و برای مبلغ صفر یا منفی mirror جدید درج نمی‌شود. برای دریافت و پرداخت، حساب مقصد/مبدأ به‌صورت ثابت حساب شماره ۱ است.

این سند درباره درستی سیاست حساب پیش‌فرض یا تخصیص تسویه به فاکتور تصمیم نمی‌گیرد.

### ۱.۳ اختلاف قطعی در نام طرف‌حساب

تابع `normalize_person` فاصله‌های متوالی را به یک فاصله تبدیل می‌کند.

در `party_balances`، query ابتدا `TRIM(customer)` را گروه‌بندی می‌کند و تابع داخلی `add` سپس نام را با `normalize_person` canonical می‌کند. در نتیجه نام legacy با فاصله داخلی دوگانه می‌تواند در خلاصه با نام canonical ادغام شود.

اما query ریزحساب در `parties_page` از شرط‌هایی مانند زیر استفاده می‌کند:

```sql
WHERE TRIM(customer)=:person
```

این شرط فاصله داخلی را normalize نمی‌کند. پس سندی با مقدار `Acme  Steel` می‌تواند در خلاصه شخص `Acme Steel` شمرده شود، اما در ریزحساب همان شخص ظاهر نشود.

این یک اختلاف قابل بازتولید در سطح query است؛ راهکار اصلاحی (canonical key پایدار، migration نام‌ها یا تغییر query) هنوز تصمیم‌گیری نشده و خارج از دامنه این سند است.

## ۲. تست پیشنهادی A — شکست sync و rollback کامل تسویه

**شناسه:** `TX-ATOMIC-SETTLEMENT-01`  
**اولویت:** بحرانی  
**محل پیشنهادی:** تست HTTP موجود در `test_transaction_reversals.py` یا یک فایل مستقل با همان harness موقت.

### پیش‌شرط

- متغیر `AHAN_DATA_DIR` پیش از import کردن `app` به یک `TemporaryDirectory` اختصاص داده شود.
- `app.init()` فقط روی همین دیتابیس موقت اجرا شود.
- یک token معتبر از `submission_token(c, 'add_settlement')` گرفته شود.
- پیش از درخواست، تعداد ردیف‌های `people`، `settlements`، `cash_movements` و `audit_log` ثبت شود.

### تزریق خطا

در تست، تابع `app.sync_cash_posting` به‌طور موقت patch شود تا فقط برای `source_table == 'settlements'` یک استثنای مشخص ایجاد کند؛ برای سایر فراخوانی‌ها رفتار اصلی حفظ شود.

سپس POST معتبر به مسیر `add_settlement` با نام شخص جدید ارسال شود.

### Assertionهای الزامی

پس از پاسخ HTTP و بازگشت تابع patch:

- تعداد `settlements` بدون تغییر باشد.
- شخص جدید در `people` باقی نمانده باشد.
- تعداد `cash_movements` بدون تغییر باشد.
- رویداد `audit_log` مربوط به `add_settlement` درج نشده باشد.
- token استفاده‌شده همچنان `consumed_at IS NULL` باشد؛ چون مصرف token نیز باید همراه تراکنش rollback شده باشد.
- `PRAGMA integrity_check` مقدار `ok` بدهد.
- `PRAGMA foreign_key_check` خالی باشد.

تست نباید فقط نبود cash mirror را بررسی کند؛ باید نبود همه اثرات جانبی سند را اثبات کند.

### کنترل مثبت مکمل

پس از برداشتن patch، همان درخواست با token تازه ارسال شود و این موارد بررسی شوند:

- دقیقاً یک settlement ثبت شود.
- دقیقاً یک cash mirror با `source_table='settlements'` و همان `source_id` وجود داشته باشد.
- جهت mirror برای `receive` برابر `deposit` و برای `pay` برابر `withdraw` باشد.
- `person_id` به شخص متناظر اشاره کند.
- رویداد audit دقیقاً یک بار درج شود.

این کنترل مثبت صرفاً رفتار فعلی مسیر را characterization می‌کند و درباره تخصیص تسویه به فاکتور ادعایی ندارد.

## ۳. تست پیشنهادی B — آشکارسازی اختلاف فاصله داخلی نام

**شناسه:** `TX-PARTY-NORMALIZATION-01`  
**اولویت:** بالا  
**محل پیشنهادی:** `test_party_ledger.py`

### داده آزمایشی

در دیتابیس موقت:

1. یک محصول آزمایشی بساز.
2. یک فروش legacy با `customer='Acme  Steel'` (دو فاصله داخلی) درج کن.
3. یک شخص canonical با نام `Acme Steel` از طریق `ensure_person` بساز.
4. هیچ داده‌ای را در دیتابیس واقعی یا فایل migration تغییر نده.

### Assertionهای characterization

- `party_balances(c)['Acme Steel']['receivable']` اثر فروش legacy را شامل شود.
- query دقیق statement با `TRIM(customer)= 'Acme Steel'` آن فروش را برنگرداند.
- نتیجه باید اختلاف بین خلاصه و statement را آشکار کند؛ تست نباید این اختلاف را به‌عنوان رفتار مطلوب برنامه تثبیت کند.
- خروجی تست/گزارش باید صریحاً با عنوان «known mismatch» یا معادل آن علامت‌گذاری شود تا با regression مطلوب اشتباه نشود.

### گیت اصلاح آتی

پس از تصمیم مالک درباره هویت canonical طرف‌حساب، یک regression test جدا باید قرارداد نهایی را assert کند. تا آن زمان، تست characterization صرفاً وجود ناسازگاری را مستند می‌کند.

## ۴. تست پیشنهادی C — تکرار هم‌زمان token در یک process

**شناسه:** `TX-TOKEN-RACE-01`  
**اولویت:** متوسط تا بالا  
**دامنه محدود:** یک process، چند thread.

- یک token واحد برای `add_settlement` تهیه شود.
- دو درخواست هم‌زمان از دو thread به همان HTTP server ارسال شوند.
- به‌علت `LOCK` فعلی، انتظار می‌رود فقط یک درخواست موفق به مصرف token برسد.
- دقیقاً یک settlement، یک cash mirror و یک audit event ثبت شود.
- درخواست دوم باید با پیام token مصرف‌شده/نامعتبر رد شود.

این تست اثبات‌کننده ایمنی چند process یا چند instance برنامه نیست. تست چندپردازه باید جداگانه و فقط پس از تصمیم درباره قید یکتا و راهبرد idempotency طراحی شود.

## ۵. موارد خارج از دامنه تست و نیازمند تصمیم

این موارد نباید در تست‌های فوق به‌عنوان سیاست حسابداری تثبیت شوند:

- تخصیص دریافت/پرداخت به یک فاکتور مشخص یا قدیمی‌ترین فاکتور؛
- اجازه یا منع مانده اعتباری مشتری؛
- انتخاب حساب مقصد/مبدأ غیر از حساب ۱ برای تسویه؛
- ادغام اشخاص دارای نام‌های نزدیک یا تغییر نام تاریخی؛
- الزام قید یکتا در `cash_movements(source_table, source_id)`؛
- رفتار چندپردازه و چندنمونه‌ای برنامه؛
- اصلاح سند با update مستقیم در برابر سند معکوس.

## ۶. ایمنی و روش اجرای آینده

- هر تست باید در process تازه و مسیر موقت مستقل اجرا شود؛ `AHAN_DATA_DIR` قبل از import `app` تنظیم شود.

## ۷. نتیجه

بازبینی کد نشان می‌دهد ثبت تسویه، مصرف token، ایجاد شخص، cash mirror و audit در یک بلوک تراکنشی واحد قرار دارند؛ بنابراین یک fault-injection test می‌تواند اتمیک بودن مسیر را به‌صورت مستقیم و قابل تکرار اثبات یا رد کند. همچنین اختلاف نام با فاصله داخلی، از تفاوت واقعی میان normalize شدن کلید خلاصه و شرط query ریزحساب ناشی می‌شود.
