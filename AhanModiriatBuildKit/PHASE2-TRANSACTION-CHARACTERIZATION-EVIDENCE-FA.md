## ۳. تفسیر و محدودیت اثبات

- تست تک‌process فقط رقابت threadها را می‌سنجد؛ تست #31 جداگانه دو process مستقل را پوشش می‌دهد.
- تست چندپردازه‌ای، دو server process روی یک فایل SQLite مشترک را بررسی می‌کند؛ ایمنی چندماشینه‌ای، شبکه‌ای یا هر معماری چندنمونه‌ای دیگر از آن نتیجه نمی‌شود.
- تست‌های token فقط مسیر `add_settlement` و route اشتباه `add_cash_movement` را در سناریوهای مشخص‌شده پوشش می‌دهند؛ این نتیجه به تمام endpointهای برنامه تعمیم داده نمی‌شود.
- تست whitespace اختلاف فعلی بین تجمیع مانده و فیلتر ریزحساب را ثبت می‌کند؛ انتخاب canonical identity، ادغام اشخاص یا اصلاح اسناد تاریخی همچنان تصمیم سیاستی باز است.
- تست rollback یک fault مشخص در `sync_cash_posting` را تزریق می‌کند؛ همهٔ نقاط شکست همهٔ مسیرهای مالی پوشش داده نشده‌اند.

## ۴. شکاف‌های باز

این زنجیره موارد زیر را حل یا اثبات نمی‌کند:

1. گزارش تشخیصی جامع برای cash mirror یتیم یا سند منبع فاقد mirror؛
2. رقابت هم‌زمان عمومی در تمام callerهای `sync_cash_posting` و تضمین uniqueness برای همهٔ source keyها؛
3. هویت canonical طرف‌حساب، تغییر نام شخص و پیوند قطعی اسناد legacy به `person_id`;
4. سیاست اصلاح/ابطال اسناد، دورهٔ بسته، تخصیص تسویه به فاکتور و انتخاب حساب؛
5. تست واقعی clean install و اجرای برنامه روی Windows کاربر، بزرگ‌نمایی ۲۰۰٪، screen reader، keyboard-only و نمایشگر کوچک.

موارد وابسته به سیاست باید تا ثبت تصمیم مالک در دفتر تصمیم‌ها باز بمانند. تست characterization نباید رفتار فعلی را به‌عنوان سیاست مطلوب تثبیت کند.
