## ۳. گیت‌های فنی و ترتیب پیشنهادی تغییر

### Gate A — قرارداد و fixtureها (بدون تغییر schema عملیاتی)

- ساخت fixtureهای کوچک با سناریوهای خرید چندمرحله‌ای، فروش، مرجوعی، تعدیل و سند تاریخ‌گذشته.
- ثبت خروجی مرجع: مقدار، ارزش کل، avg مشتق‌شده، COGS، ماندهٔ اشخاص، ماندهٔ هر حساب.
- تست‌های golden باید بدون UI و با محاسبهٔ مستقل از توابع production اجرا شوند تا خطای مشترک تست/کد پنهان نماند.

### Gate B — موتور ارزش‌گذاری مستقل

- سرویس خالص برای اعمال رویدادهای خرید، فروش، مرجوعی و تعدیل روی `quantity` و `total_value_rial`.
- هیچ SQL یا HTML در موتور محاسبه قرار نگیرد.
- خروجی موتور شامل مقدار قبل/بعد، ارزش قبل/بعد، بهای واحد مشتق‌شده و دلیل/نوع رویداد باشد.
- ابتدا با fixtureها و shadow comparison روی کپی DB سنجیده شود؛ هنوز products cache را تغییر ندهد.

### Gate C — دفتر و مهاجرت سایه

- ledgerها را کنار جداول فعلی بساز؛ برای هر سند قدیمی candidate event تولید کن.
- تعداد و مجموع مقدار/ارزش و مانده‌ها را بین مسیر قدیم و جدید مقایسه کن.
- موارد مبهم (مثلاً موجودی افتتاحیه بدون سند یا capital/cash conflation) در exception report بمانند؛ حدس خودکار ممنوع.
- تا زمان رسیدن به تطبیق کامل یا تصویب اختلاف‌های مستند، منبع خواندن برنامه عوض نشود.

### Gate D — سوییچ کنترل‌شدهٔ سرویس‌ها

- پس از تطبیق، نوشتن از مسیرهای واحد سرویس عبور کند.
- cacheهای قدیمی فقط projection باشند و rebuild آن‌ها idempotent باشد.
- مسیرهای مستقیم update/delete بسته شوند.
- API/فرم‌ها فقط ورودی بگیرند؛ تصمیم حسابداری داخل service layer باشد.

### Gate E — اصلاح/ابطال و allocation

- ابتدا postingها و allocationها مدل شوند، سپس routeهای ثبت/اصلاح/ابطال به آن متصل شوند.
- unique source reference و idempotency در سطح دیتابیس تضمین شود؛ فقط token فرم کافی نیست.
- تست هم‌زمانی/retry و rollback transaction اضافه شود.

## ۴. ریسک‌های ترتیب و وابستگی

1. **اولویت ارزش‌گذاری قبل از اصلاح مرجوعی:** fix محلی ACC-48 بدون total-value ledger فقط یک اصلاح نقطه‌ای است و با backdated docs یا هزینهٔ جانبی ممکن است دوباره ناسازگار شود.
2. **افتتاحیه قبل از ledger:** ثبت opening stock در جدول جدید بدون منبع ارزش/واحد دقیق، خطای تاریخی را تثبیت می‌کند.
3. **ابطال قبل از مرجع posting:** اگر سند معکوس cash/inventory source یکتا نداشته باشد، reversal ممکن است وجه را دوباره برگرداند.
4. **allocation قبل از پاکسازی منطق paid/received:** نگه‌داشتن هم‌زمان اثر فاکتور و settlement می‌تواند مانده را دو بار تغییر دهد.
5. **تغییر cache قبل از shadow comparison:** بازنویسی products.stock/avg_cost بدون گزارش تطبیق قابل برگشت و قابل اثبات نیست.
