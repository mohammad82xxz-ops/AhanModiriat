این سند expected resultهای عددی و سناریوهای پذیرش را تعریف می‌کند تا تست‌ها صرفاً مسیر HTTP را بررسی نکنند و محاسبات را با همان تابع production تکرار نکنند. اعداد بر حسب ریال‌اند و مقدار کالا در واحد پایهٔ فرضی است. هیچ‌یک از این سناریوها به معنی تصویب سیاست‌های DEC-01 تا DEC-10 نیست.

## ۱. قرارداد اجرای سناریوها

- هر سناریو باید روی دیتابیس تست مستقل اجرا شود؛ وابستگی به ترتیب اجرای تست‌ها ممنوع.
- محاسبهٔ expected result باید در خود تست با اعداد ثابت/فرمول مستقل انجام شود؛ فراخوانی تابع محاسبهٔ production برای ساخت expected ممنوع.
- تمام عملیات در یک transaction اتمیک باشند؛ شکست در میانه نباید سند نیمه‌کاره باقی بگذارد.
- پس از هر سناریو، هم ماندهٔ cache و هم جمع دفتر رویداد باید کنترل شوند.
- برای پول، واحد ذخیره‌سازی ریال صحیح است. گردکردن فقط در مرز تعریف‌شده و طبق قاعدهٔ مصوب انجام شود.
- برای مقدار، تا تصویب مهاجرت واحد پایه، از اعداد صحیح ساده استفاده شود؛ این سند دربارهٔ تبدیل وزن واقعی آهن‌آلات به گرم حکم نمی‌دهد.
- رویدادهای ابطال‌شده از ماندهٔ مؤثر کنار گذاشته شوند، اما اصل و سند معکوس هر دو در تاریخچه باقی بمانند.

## ۷. آزمون migration، restore و invariant

### MIG-01 — shadow comparison

- روی کپی دیتابیس قدیمی، رویدادهای candidate از اسناد موجود ساخته شوند.
- تعداد سندهای تبدیل‌شده، مقدار و ارزش، ماندهٔ اشخاص و ماندهٔ هر حساب قبل/بعد گزارش شود.
- هر دادهٔ مبهم در exception report بماند؛ صفرکردن اختلاف با repair حدسی ممنوع.

### MIG-02 — اجرای دوبارهٔ migration

**Expected:** اجرای دوم هیچ رویداد افتتاحیه/خرید/فروش/تعدیل تکراری نسازد؛ checksum و counts ثابت بماند.

### RESTORE-01 — candidate دارای orphan FK

**Expected:** restore پیش از جایگزینی دیتابیس رد شود؛ دیتابیس فعلی و backup دست‌نخورده بمانند.

### INV-CHECK-01 — invariant جامع پس از هر سناریو

- مقدار کالا = افتتاحیه + مجموع رویدادهای مقداری معتبر.
- ارزش کالا = افتتاحیهٔ ارزش + مجموع رویدادهای ارزش معتبر.
- avg_cost فقط projection ارزش/مقدار باشد؛ برای مقدار صفر، قاعدهٔ صریح صفر/موجودی بدون ارزش اعمال شود.
- ماندهٔ شخص = افتتاحیه + اسناد − تخصیص دریافت/پرداخت.
- ماندهٔ حساب = افتتاحیه + ورودی − خروجی.
- مجموع تخصیص‌های هر receipt/payment از مبلغ سند تجاوز نکند و در حالت نهایی برابر مبلغ تخصیص‌یافته باشد.
- هر posting دارای source یکتا و مرجع معتبر باشد.
- مجموع reversal هر سند از اثر اصلی بیشتر نشود؛ reversal تکراری ممنوع.
- تمام foreign keyها معتبر و همهٔ مقادیر پولی در محدودهٔ INTEGER ریال باشند.

## ۹. معیار آمادگی تست برای CI

- همهٔ سناریوهای مصوب باید تست خودکار شوند؛ موردی که سیاست آن مصوب نیست باید صریحاً pending بماند، نه اینکه silently skip شود.
- هر test id در نام تست یا marker قابل جست‌وجو باشد.
- در شکست، expected/actual مقدار، ارزش، مانده و شناسهٔ سند چاپ شود.
- حداقل یک تست property-based برای idempotency و invariant دفتر مقدار/ارزش اضافه شود.
- تست‌های integration از UI مستقل باشند؛ سپس حداقل یک تست HTTP end-to-end برای هر جریان اصلی اجرا شود.
- CI روی آخرین SHA و fixtureها باید موفق باشد؛ CI موفق جایگزین تصویب سیاست و بازبینی حسابداری نیست.
