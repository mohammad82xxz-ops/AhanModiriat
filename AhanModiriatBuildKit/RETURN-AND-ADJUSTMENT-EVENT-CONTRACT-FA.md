# قرارداد عملیاتی رویدادهای مرجوعی و تعدیل موجودی

> **وضعیت:** پیشنهاد طراحی و قرارداد پذیرش — نیازمند تصویب مالک؛ هیچ سیاست حسابداری در این سند مصوب نیست.
> **شناسه تصمیم پیشنهادی:** DEC-14
> **دامنه:** مرجوعی خرید، مرجوعی فروش، کسری و اضافی انبار؛ ارتباط با اسناد منبع، مقدار، ارزش، تسویه و ردیابی.
> **وابستگی‌ها:** DEC-01، DEC-02، DEC-03، DEC-04، DEC-09، DEC-10، DEC-11، DEC-12 و DEC-13.
> **مرز ایمنی:** این سند طراحی است؛ کد، schema، migration یا دادهٔ عملیاتی را تغییر نمی‌دهد.

## ۱. هدف و اصل تفکیک

هر رویداد انبار ممکن است هم‌زمان چند اثر متفاوت داشته باشد. سیستم نباید این اثرها را در یک عدد یا یک مفهوم ادغام کند:

1. **اثر مقداری:** مقدار پایه‌ای که وارد یا از انبار خارج می‌شود.
2. **اثر ارزشی دفتر موجودی:** ارزش دفتری ورود یا خروج طبق روش مصوب DEC-12.
3. **اثر حساب طرف‌حساب:** بدهکار/بستانکار شدن مشتری یا تأمین‌کننده طبق سند تجاری.
4. **اثر نقد/تسویه:** دریافت یا پرداخت واقعی؛ ممکن است در زمان مرجوعی انجام نشود.
5. **اثر سود و زیان/اختلاف:** تفاوت مبلغ توافق‌شده با ارزش دفتری یا هزینهٔ مرتبط.
6. **اثر ردیابی:** اتصال رویداد به سند اصلی، ردیف اصلی، actor، زمان ثبت و تاریخ مؤثر.

ثبت یک مرجوعی به معنی انجام خودکار وجه نقد نیست. ثبت تعدیل موجودی نیز به معنی خرید یا فروش تجاری نیست.

## ۲. واژگان و قرارداد مشترک

- **Source document:** سند اصلی خرید/فروش یا صورت‌جلسهٔ تعدیل.
- **Source line:** ردیف مشخص سند که مقدار و کالا/مارک آن را تعیین می‌کند.
- **Return authorization:** مجوز مرجوعی با علت، مقدار مجاز و تأییدکننده.
- **Returned quantity:** مقدار فیزیکی تحویل‌گرفته/تحویل‌داده‌شده و تأییدشده.
- **Accepted quantity:** مقدار نهایی پذیرفته‌شده پس از کنترل کیفیت/مغایرت.
- **Remaining returnable quantity:** مقدار قابل مرجوعی باقی‌مانده از ردیف اصلی.
- **Inventory carrying value:** ارزش دفتری ورود/خروج موجودی.
- **Commercial settlement amount:** مبلغ بستانکاری/بدهکاری طرف‌حساب در سند تجاری.
- **Adjustment evidence:** صورت‌جلسه شمارش، علت و شواهد تعدیل.
- **Posting:** ثبت نهایی و غیرقابل‌ویرایش مستقیم رویداد در دفتر.

مقادیر درخواست‌شده، تحویل‌شده، پذیرفته‌شده و ثبت‌شده باید قابل تفکیک باشند؛ درخواست مرجوعی به‌تنهایی نباید موجودی را تغییر دهد.

## ۳. قرارداد مشترک دادهٔ رویداد

حداقل اطلاعات مفهومی هر رویداد:

| گروه | فیلد/اطلاعات | قاعده |
|---|---|---|
| هویت | event_id | شناسهٔ یکتا و پایدار |
| نوع | event_type | purchase_return / sales_return / adjustment_in / adjustment_out |
| منبع | source_document_type, source_document_id | سند اصلی یا مرجع تعدیل |
| ردیف | source_line_id | در مرجوعی تجاری، ردیف اصلی؛ در تعدیل، ردیف صورت‌جلسه |
| کالا | product_id و snapshot واحد/ضریب | هویت کالا و تبدیل تاریخی حفظ شود |
| مقدار | requested, received/delivered, accepted, posted | وضعیت‌های مقدار مخلوط نشوند |
| زمان | effective_at, recorded_at, ledger_sequence | تاریخ اثر، زمان ثبت و ترتیب دفتر مستقل باشند |
| ارزش | inventory_value_delta | delta ارزش دفتری، با علامت و واحد روشن |
| تسویه | settlement_amount | مبلغ تجاری مستقل از ارزش دفتری |
| علت | reason_code, description | علت ساخت‌یافته و توضیح |
| کنترل | actor, approver, approved_at | عامل و تأییدکننده |
| وضعیت | draft/authorized/posted/reversed | وضعیت گردش کار |
| تکرار | idempotency/source_key | جلوگیری از ثبت تکراری |
| اصلاح | reversal_of_event_id | اصلاح از مسیر معکوس/جایگزین مصوب |

این جدول قرارداد مفهومی است؛ نام ستون‌های واقعی و مدل schema در مرحلهٔ طراحی فنی تعیین خواهد شد.

## ۴. مرجوعی خرید — Purchase Return

### ۴.۱ چرخهٔ وضعیت

پیشنهاد چرخه:

`Draft → Requested → Authorized → Received/Inspected → Accepted → Posted`

رد کامل یا جزئی باید علت و actor داشته باشد. تنها مرحلهٔ Posting مجاز است موجودی و دفتر مالی را تغییر دهد. لغو قبل از Posting، اثر موجودی ندارد. اصلاح بعد از Posting از مسیر reversal/replacement طبق DEC-09 انجام می‌شود.

### ۴.۲ کنترل مقدار

- مرجوعی باید به ردیف خرید اصلی متصل باشد؛ اگر اتصال ممکن نیست، دلیل و مجوز استثنا لازم است.
- مجموع مقدار مرجوعی‌های posted و معتبر برای یک ردیف نباید از مقدار خرید پذیرفته‌شده، پس از کسر ابطال/برگشت‌های قبلی، بیشتر شود.
- چند مرجوعی جزئی مجاز است؛ کنترل باید aggregate و اتمیک باشد تا دو درخواست هم‌زمان از سقف عبور نکنند.
- مقدار مرجوعی با snapshot واحد/ضریب زمان سند اصلی و واحد پایه ثبت شود.
- اگر کالا در انبار موجود نیست یا بخشی از آن فروخته شده، سیاست اجازه/محدودیت باید مستقل و صریح باشد؛ موجودی منفی خودکار ایجاد نشود.
- اختلاف مقدار تحویل‌شده و پذیرفته‌شده در وضعیت inspection/exception باقی بماند و فقط مقدار پذیرفته‌شده طبق سیاست وارد posting شود.

### ۴.۳ تفکیک ارزش

حداقل سه مقدار مستقل:
1. مقدار و ارزش دفتری خروج از موجودی؛
2. مبلغ credit note یا بستانکاری مورد توافق با تأمین‌کننده؛
3. اختلاف ارزش دفتری و مبلغ تجاری و حساب مقابل آن.

مبنای ارزش دفتری باید از DEC-01 و DEC-12 تبعیت کند؛ گزینه‌های تاریخی خرید، میانگین جاری یا مبلغ توافق‌شده هنوز Pending هستند. مبلغ تسویه نباید بدون تصمیم حسابداری به‌جای carrying value بنشیند.

### ۴.۴ سناریوهای خاص

- خرید اصلی چندبار مرجوعی شده است.
- مرجوعی از چند ردیف خرید با قیمت متفاوت انجام می‌شود.
- ردیف خرید اصلی اصلاح یا معکوس شده است.
- بخشی از کالا آسیب‌دیده یا غیرقابل‌قبول است.
- مرجوعی در تاریخ مؤثر گذشته ثبت می‌شود.
- credit note با مبلغ خروج موجودی متفاوت است.
- تأمین‌کننده کالا را تحویل گرفته اما تسویه را به آینده موکول کرده است.

در هر مورد، مرجع اصلی، مقدار باقی‌ماندهٔ قابل برگشت، تاریخ اثر و ارزش‌گذاری باید قابل بازسازی باشند.

## ۵. مرجوعی فروش — Sales Return

### ۵.۱ چرخهٔ وضعیت

پیشنهاد چرخه:

`Draft → Requested → Authorized → Received/Inspected → Accepted → Posted`

درخواست مشتری به‌تنهایی موجودی را افزایش نمی‌دهد. کالای تحویل‌شده باید از نظر مقدار، هویت، کیفیت و قابلیت فروش مجدد بررسی شود. مقدار پذیرفته‌نشده نباید به موجودی قابل فروش اضافه شود؛ وضعیت قرنطینه/ضایعات باید طبق سیاست انبار تعریف شود.

### ۵.۲ کنترل مقدار

- مرجوعی به فاکتور و ردیف فروش اصلی متصل شود.
- مجموع مرجوعی‌های پذیرفته‌شده از مقدار فروخته‌شدهٔ خالص همان ردیف بیشتر نشود.
- برای چند مرجوعی جزئی، ماندهٔ قابل برگشت به‌صورت اتمیک کنترل شود.
- اگر فاکتور چندبار اصلاح/ابطال شده، مرجع به نسخهٔ معتبر نهایی یا زنجیرهٔ سند اصلاحی اشاره کند.
- کالای برگشتی از مشتری، تا پایان بازرسی نباید به‌طور پیش‌فرض قابل فروش تلقی شود.
- مرجوعی بدون فاکتور اصلی فقط با workflow استثنا، دلیل و تأیید مجاز باشد؛ اتصال ساختگی به فاکتور نامرتبط ممنوع است.

### ۵.۳ تفکیک ارزش

حداقل این اثرها جدا باشند:
1. ارزش دفتری ورود مجدد کالا به موجودی یا ارزش ورود به وضعیت قرنطینه؛
2. مبلغ بستانکاری/استرداد مشتری؛
3. برگشت یا اصلاح COGS و اثر سود ناخالص طبق DEC-12 و سیاست مصوب؛
4. هزینهٔ آسیب/افت کیفیت در صورت وجود و حساب مقابل آن.

بهای ثبت‌شده در فروش اصلی باید قابل بازیابی بماند؛ استفاده از میانگین جاری به‌جای cost basis فروش یا برعکس، فقط مطابق گزینهٔ مصوب DEC-01/DEC-12 مجاز است. مبلغ refund مشتری الزاماً برابر ارزش ورود مجدد به موجودی نیست.

### ۵.۴ سناریوهای خاص

- فروش با چند ردیف یک کالای هم‌نام/واحد متفاوت.
- فروش جزئی، مرجوعی چندمرحله‌ای و برگشت کامل.
- کالای سالم، آسیب‌دیده، ناقص یا غیرقابل‌فروش.
- کالا پس از فروش با بهای جاری متفاوت برگشت می‌خورد.
- refund فوری، credit به حساب مشتری یا تهاتر با فاکتور بعدی.
- مرجوعی پس از بسته‌شدن دورهٔ فروش.
- فاکتور اصلی reversal شده یا مشتری فقط بخشی از کالا را تحویل داده است.

## ۶. تعدیل منفی — کسری انبار

### ۶.۱ منبع و علت

تعدیل منفی باید از صورت‌جلسهٔ شمارش یا مجوز قابل ردیابی ناشی شود و حداقل شامل:
- انبار/محل و محدودهٔ شمارش؛
- مقدار دفتری در لحظهٔ شمارش؛
- مقدار فیزیکی شمارش‌شده؛
- اختلاف مقدار در واحد پایه؛
- علت ساخت‌یافته (پرت/برش، ضایعات، آسیب، خطای اندازه‌گیری، سرقت مشکوک، خطای ثبت، علت نامعلوم)؛
- شواهد و توضیح؛
- شمارش‌کننده و تأییدکننده مستقل در صورت لزوم.

علت «نامعلوم» باید مجاز ولی پرچم‌دار باشد؛ سیستم نباید علت را حدس بزند.

### ۶.۲ کنترل مقدار و ارزش

- تعدیل منفی نباید از مقدار موجود قابل تعدیل بیشتر باشد، مگر سیاست موجودی منفی به‌طور مستقل تصویب شده باشد.
- اختلاف شمارش باید قبل از posting با snapshot همان نقطهٔ cut-off تطبیق شود.
- ارزش خروج از موجودی طبق DEC-02 و DEC-12 تعیین می‌شود؛ میانگین جاری فقط یکی از گزینه‌های Pending است.
- مبلغ خسارت، مطالبه از مسئول یا بیمه، در صورت وجود، با ارزش دفتری خروج ادغام نشود.
- ثبت تعدیل باید اثر مقدار و اثر ارزش را با علت و حساب مقابل مشخص کند.

## ۷. تعدیل مثبت — اضافی انبار

### ۷.۱ منبع و علت

افزایش موجودی بدون سند خرید متناظر نباید به‌صورت خرید ساختگی ثبت شود. منبع می‌تواند شمارش مجدد، کشف کالای ثبت‌نشده، اصلاح واحد، انتقال داخلی جاافتاده یا خطای ثبت باشد؛ هر علت workflow و حساب مقابل متفاوتی ممکن است داشته باشد.

حداقل مدرک:
- صورت‌جلسهٔ شمارش و محل؛
- مقدار دفتری/فیزیکی و اختلاف؛
- شواهد منشأ، اگر معلوم است؛
- مقدار پایه و واحد/ضریب؛
- ارزش مورد تأیید یا وضعیت unresolved؛
- actor و approver.

### ۷.۲ کنترل مقدار و ارزش

- اگر اختلاف ناشی از انتقال داخلی جاافتاده است، باید منبع و مقصد با هم تطبیق شوند؛ افزایش یک انبار نباید بدون کاهش متناظر انبار دیگر دوباره ثبت شود.
- اگر مقدار معلوم ولی ارزش نامعلوم است، وضعیت VALUE_UNRESOLVED/تعلیقی مطابق DEC-03 و DEC-11 استفاده شود؛ ارزش حدسی وارد بهای موجودی قطعی نشود.
- ارزش ورود و حساب مقابل طبق DEC-03 و سیاست مصوب تعیین شود.
- تعدیل مثبت نباید به‌طور خودکار به درآمد، خرید یا سرمایه تبدیل شود.

## ۸. ترتیب، دوره و اصلاح اسناد

- همهٔ رویدادها باید effective_at، recorded_at و ledger_sequence مستقل داشته باشند؛ سیاست نهایی DEC-12 مرجع است.
- رویداد backdated باید طبق DEC-04/DEC-10 یا replay کامل داشته باشد یا به‌صورت اتمیک رد/محدود شود.
- posting نهایی immutable تلقی شود؛ اصلاح از طریق reversal/replacement و اتصال به رویداد اصلی انجام شود.
- reversal باید deltaهای معکوس، علت، actor، زمان ثبت و ارتباط به اصل را داشته باشد؛ سند اصل حذف نشود.
- رویدادهای وابسته به هم (مثل برگشت انتقال) باید group/correlation id داشته باشند تا نیمه‌ثبت نشوند.
- ثبت دوگانه با source key و idempotency کنترل شود.

## ۹. گیت‌های تأیید و دسترسی

پیشنهاد نقش‌ها (نیازمند تأیید):
- **درخواست‌کننده:** ایجاد پیش‌نویس و ثبت علت.
- **بازرس/تحویل‌گیرنده:** ثبت مقدار تحویل‌شده و پذیرفته‌شده.
- **تأییدکننده:** بررسی مدرک و تأیید posting؛ در تعدیل بااهمیت ترجیحاً متفاوت از درخواست‌کننده.
- **ثبت‌کننده:** اجرای posting پس از مجوز.
- **ممیز:** مشاهدهٔ trail و گزارش بدون دسترسی به تغییر سند.

حدود مبلغ/مقدار، تفکیک وظایف، سطح مدیر و تأیید دوم هنوز باید توسط مالک تعریف شود. این نقش‌ها پیشنهاد معماری‌اند و نقش واقعی سیستم را توصیف نمی‌کنند.

## ۱۰. سناریوهای پذیرش و آزمون

تمام تست‌ها باید روی fixture مصنوعی و دیتابیس موقت انجام شوند. expectedهای وابسته به سیاست تا تصویب DECها Pending هستند.

| شناسه | سناریو | assertion فنی |
|---|---|---|
| RET-01 | دو مرجوعی جزئی خرید از یک ردیف | مجموع posted از مقدار مجاز خرید تجاوز نکند |
| RET-02 | دو درخواست هم‌زمان برای آخرین مقدار قابل برگشت | فقط درخواست‌های داخل سقف مجاز شوند؛ race condition ثبت اضافه نسازد |
| RET-03 | مرجوعی خرید از چند ردیف با بهای متفاوت | اتصال ردیف و ارزش هر بخش مستقل حفظ شود |
| RET-04 | مقدار تحویل‌شده بیشتر از مقدار پذیرفته‌شده | فقط مقدار پذیرفته‌شده posting شود؛ باقی‌مانده exception بماند |
| RET-05 | مرجوعی خرید با credit note متفاوت از carrying value | ارزش دفتری و مبلغ تسویه جدا و اختلاف آشکار باشد |
| RET-06 | مرجوعی فروش جزئی چندمرحله‌ای | مجموع accepted از مقدار خالص فروخته‌شده بیشتر نشود |
| RET-07 | کالای برگشتی آسیب‌دیده | به موجودی قابل فروش اضافه نشود مگر پس از disposition مجاز |
| RET-08 | refund مشتری با ورود مجدد موجودی متفاوت | مبلغ refund و inventory value دو اثر مستقل داشته باشند |
| RET-09 | مرجوعی بدون سند اصلی | رد یا workflow استثنای مصوب؛ سند منبع جعلی نسازد |
| RET-10 | مرجوعی پس از reversal فاکتور اصلی | زنجیرهٔ سند معتبر تشخیص داده و double return مسدود شود |
| ADJ-01 | کسری بیشتر از موجودی دفتری | posting عادی رد شود؛ مسیر موجودی منفی فقط با سیاست مستقل |
| ADJ-02 | تعدیل منفی با علت نامعلوم | علت نامعلوم صریح و پرچم‌دار؛ مقدار/ارزش همچنان قابل ردیابی |
| ADJ-03 | تعدیل مثبت با ارزش نامعلوم | موجودی unresolved/تعلیقی؛ ارزش حدسی وارد موجودی قطعی نشود |
| ADJ-04 | انتقال داخلی ثبت‌نشده بین دو انبار | اثر دوطرفه در یک گروه اتمیک؛ جمع کل شرکت دوباره‌شماری نشود |

### آزمون‌های property-based پیشنهادی

1. **Return cap:** مجموع accepted returns هر source line هیچ‌گاه از مقدار خالص قابل برگشت فراتر نرود.
2. **Idempotency:** تکرار یک درخواست posting با source key یکسان هیچ delta جدید نسازد.
3. **Atomicity:** یا تمام اثرهای رویداد ثبت شوند یا هیچ‌کدام.
4. **Reversal conservation:** رویداد + reversal کامل، delta خالص صفر بسازند؛ trail هر دو باقی بماند.
5. **Source traceability:** هر delta تجاری به source line معتبر و هر delta تعدیل به evidence/authorization وصل باشد.
6. **Warehouse conservation:** انتقال داخلی، جمع مقدار کل انبارها را تغییر ندهد؛ مگر اختلاف مستقل و مصوب وجود داشته باشد.
7. **Deterministic replay:** همان رویدادها، ترتیب و نسخهٔ سیاست خروجی یکسان بدهند.
8. **No guessed valuation:** نبود ارزش معتبر باید وضعیت unresolved تولید کند، نه مبلغ حدسی.
